# 下载与删除的性能优化

2026-10-29。

下载进度每约 350 毫秒更新一次。旧实现每次从 JSON 重新解析整条下载记录，包括来源、请求头和检查点；下载页还重复按时间、状态排序。删除记录虽然已有分组提交，但后台每清理一个任务仍分别提交原生移除标记和缓存移除标记，逐次加密、刷新整个本地状态文件。勾选删除已保存文件时，也会逐条提交记录。

## 调整

- 进度、速度和阶段更新直接复制任务，保留不变的来源和检查点对象；状态及来源变更继续使用原解析规则。进度未变化时减少界面通知，工作连接数变化仍立即通知。原有进度保存周期保持不变。
- 缓存任务的创建时间顺序，仅新增、删除或重新导入时重排。每次读取仍返回独立列表，包含最新状态；界面按状态分组，保持组内时间倒序。
- 没有活动写入的任务，每最多 64 项合并删除记录与清理标记的提交。真实文件仍逐项删除；失败保留记录和原路径，取消会完成当前项并保留后续项。
- 原生和缓存清理成功后，每最多 64 项合并确认。失败项及清理期间新增的标记保留；关闭应用时提交已完成的不足一组部分。冷启动清理已有原生标记也只提交成功项。

取链、线程配置、网盘限制、文件校验、暂停续传和边下边播沿用现有流程。正在写入的任务仍先停止写入，再提交删除；只移除记录时保留已保存文件。选中删除文件但状态写入失败时，记录保持可重试，重复删除已不存在的文件不会误删其他文件。

## 保存阶段：同卷不再复制（2026-11-03）

用户反馈 Linux 上 1 GB 文件下载完成后的「保存文件」要跑约一分钟，且一个文件保存完后常要等十几秒才开始下一个的保存。

下载的字节先落在 `<下载目录>/.asterlink-cache/<id>/`，完成后再「发布」到 `<下载目录>`。两者在同一个目录树里，发布本可以是硬链接——零拷贝、瞬时完成。但 `storagePlan()` 只会用 `GetVolumePathNameW` / `CreateHardLinkW` 那一套问 Windows，非 Windows 拿到 `supportsHardLinks = false`，`copyOnSave` 因此**恒为 true**：每个文件都被完整读一遍再写一遍。

三处修改：

1. 新增 `lib/platform/posix_storage.dart`，用 FFI 调 libc 的 `stat`（取 `st_dev`，判断缓存与目标是否同一文件系统）和 `link`（发布硬链接）。`storagePlan()` 在非 Windows 上改用它；取不到设备号时仍回退到「一律复制」这一保守行为。
2. `save()` 的硬链接分支按平台分发；硬链接失败且目标不存在（exFAT、FAT32、部分网络盘）时**退回复制**，不再抛错。
3. 复制分支从 `openRead()`（64 KiB 一块）换成 `readInto` + 1 MiB 缓冲。

同一个 1.07 GB 文件，本机 NVMe、ext4：

| 发布方式 | 耗时 | 吞吐 |
| --- | ---: | ---: |
| `openRead()` 64 KiB（旧） | 5.76 s | 186 MB/s |
| `readInto` 1 MiB | 2.34 s | 459 MB/s |
| `link()` 硬链接 | < 1 ms | — |

用户机器上的 17 MB/s 量级说明那份缓存和目标当时并不是同盘，或磁盘本身更慢；同卷硬链接后该步骤直接从秒级消失，跨卷复制也快了约 2.5 倍。

### 为什么下一个文件要等十几秒

保存放在一个全局串行段里（`_acquirePost` / `_releasePost`，保证同一时刻只有一个任务在校验和发布）。`_afterCompleted()` 原本在这个段**内**执行，它要做两件慢事：删掉整份缓存文件（GB 级 unlink）、等 `CleanupOutbox.ready()`。于是下一个已经下完的任务必须等前一个把这些做完才能开始保存。

现在 `_releasePost()` 之后再做清理，异常也不冒泡成「下载失败」。清理只碰自己那份缓存目录（`_cacheAccess[id]` 按 id 加闸），与下一个任务的保存互不影响；`StateStore.change` 与 `CleanupOutbox.drain` 各自有串行闸，并发调用安全。

### 预留策略：按卷实测，不按文件系统名猜

同卷时目标卷不再预留「第二份」，只按缓存侧计算空间需求——这正是硬链接的意义，之前 80 GB 文件要 160 GB 空闲才肯下载。

但「同卷就能硬链接」是个假设，而不是事实。第一版把 `supportsHardLinks` 直接定义为 `st_dev != null`，于是 exFAT、FAT32、部分网络盘的预留也只有一份，真正失败要等到保存阶段（那时字节早已落盘，退回复制才报空间不足，等于白下）。

现在改为**实测一次、按设备号缓存**（`PosixStorage.supportsHardLinks`）：在目标目录里写一个 0 字节文件、给它建第二个名字、立刻删掉，两个 dirent 的代价，每个 `st_dev` 每个进程只做一次。失败（EPERM/ENOTSUP 等）则 `copyOnSave = true`，预留回到两份，与 `save()` 的真实行为一致。`ENOSPC`/`EDQUOT` 例外：那是盘满了，而 `link()` 本身不占数据块，仍按可链接处理，避免「盘满」被误判成「复制一份」。

本机三种卷实测（`dart run tool/posix_storage_check.dart <目录>`）：

| 卷 | 文件系统 | `st_dev` | 硬链接 | 发布后删缓存 | 重名 |
| --- | --- | ---: | --- | --- | --- |
| `/home/jiah` | ext4 | 66309 | 可用 | 目标仍可读 | 抛错、不覆盖 |
| `/media/jiah/新加卷` | NTFS（ntfs-3g，`fuseblk`） | 66310 | 可用 | 目标仍可读 | 抛错、不覆盖 |
| `/dev/shm` | tmpfs | 94 | 可用 | 目标仍可读 | 抛错、不覆盖 |

NTFS 用 `fuseblk` 挂载时走的是 ntfs-3g，硬链接是原生 NTFS 功能，`ln` 与清单里的三项全部正常；换成内核 `ntfs3` 驱动或其他挂载方式时不需要改代码——探针会自己得出结论。不可写的目录（如 `/boot/efi`、`/home` 根）探针直接失败，落回复制，这也是安全方向。

### 保存阶段：文件名必须按字节截断（2026-11-03）

用户反馈：夸克网盘一次下多个文件，最后一个约 1.6 GB 的文件「校验完成、开始保存」时报「读写文件失败，请检查存储空间和目录权限」。磁盘空余 100+ GB、目录权限正常（同批其他文件都保存成功），后来另一个 700 MB 文件也正常。该问题在保存优化之前就存在。

报错来自 `download_manager.dart` 对 `FileSystemException` 的统一兜底，而抛点就在 `save()` 里**第一个用到原始文件名**的地方——缓存侧写的是固定名 `payload`，所以名字问题只会在发布这一刻暴露，而且是在整份字节落盘、校验通过之后，看着就像"空间/权限"问题。

根因是 `safeFileName()` 按**字符**截断（`name.length > 180` → 取前 160 字符），而限制是按**字节**的：

| 文件系统 | 单分量上限 | 超限报错 |
| --- | ---: | --- |
| ext4 | 255 字节 | `ENAMETOOLONG` (36) |
| NTFS（ntfs-3g，`fuseblk`） | 255 **字符** | `ENAMETOOLONG` (36) |

160 个中文字符 = 480 字节：ext4 直接拒绝（> 255 字节），NTFS 反而收得下（160 ≤ 255 字符）。影视类资源名普遍 60–150 个中文字符，所以症状是"偶发一个文件、跟大小无关"——1.6 GB 只是巧合，用户的下载目录在 ext4 上才暴露。

修改：

1. `safeFileName()` 改为按 UTF-8 字节预算截断（`_nameByteLimit = 240`，`_collisionRoom = 12` 留给 `save()` 重名时追加的 ` (10000)`），并且**只在字符边界切**——切在多字节字符中间会得到非法 UTF-8，ntfs-3g 连建都不建。
2. 扩展名超过 40 字节时丢弃而不是保留；截断后重新去掉尾随的 `.`/空格（NTFS 不接受）。
3. `download_manager.dart` 把 `ENAMETOOLONG` 从通用文案里分出来，给出「文件名或保存路径过长」的明确提示（ntfs-3g 报 EPERM 时仍是通用文案，但修好后不应再触发）。

本机实测（同一脚本跑旧实现与新实现对照，ext4 + NTFS 两块盘，含 ` (1)` 重名变体；errno 取裸 `openat` 的真实值）：

| 原始名 | 旧实现 | ext4 | NTFS | 新实现 | ext4 | NTFS |
| --- | ---: | --- | --- | ---: | --- | --- |
| 160 个汉字（480 B） | 480 B | **ENAMETOOLONG (36)** | OK | 228 B | OK | OK |
| 300 个 ASCII + `.zip`（304 B） | 164 B | OK | OK | 228 B | OK | OK |
| 79 字长中文 + `.mkv`（214 B） | 214 B | OK | OK | 214 B | OK | OK |
| 短中文 / 短 ASCII | 不变 | OK | OK | 不变 | OK | OK |

NTFS 那列值得注意：旧实现并不是在所有盘上都失败——160 字符的中文名在 ntfs-3g 上完全合法（255 字符上限），只有 ext4 这类按字节算的才拦。同一个文件换个盘存就能成功，这也是它"偶发"的原因之一。

遗留边界：`safeRelativePath()` 现在保证**每一段** ≤ 228 字节，但没有限制整条路径长度。极端深的目录树仍可能撞 `PATH_MAX`，届时同样表现为这条报错；需要时再加总长校验。
